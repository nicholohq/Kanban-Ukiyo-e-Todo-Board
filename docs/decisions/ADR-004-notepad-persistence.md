# ADR-004: Notepad Persistence

## Status

Accepted

## Date

2026-10-16

## Context

The notepad adds a second kind of user content — long-form notes — beside the
task board. A note is a document: the user types continuously into it, reads it
back later, and expects edits to survive a refresh. That is a materially
different usage pattern from a task, which is a small record edited through a
form and committed on submit.

Persistence for tasks already has a settled shape. ADR-003 established the
storage facade and its adapters; the task API is a small set of REST routes over
the Turso database. The notepad needs somewhere to live in both places — locally
and on the server — and the choices made there have to stay consistent with what
tasks already do, because the two share one store, one snapshot, and one
synchronisation cycle.

This record captures those choices.

## Decision

### 1. A `notes` table and `/api/notes` endpoints, modelled on the task routes

The server gains a `notes` table and `/api/notes` routes shaped like the
existing task routes — a collection read, and per-record write and delete. There
is one deliberate difference: the **note id is generated by the client** and sent
to the server, which stores it as given rather than minting its own. Tasks have
the server assign identity; notes do not, because notes are merged on load by
matching ids (see §3), and a merge keyed on ids cannot work if the two sides
disagree about what those ids are.

### 2. `todoStore` remains the single snapshot writer, and now saves notes too

`todoStore` is still the only writer of the persisted snapshot; it now includes
the note set and the active note id in the snapshot it writes. `notesStore`
holds note state in memory and drives synchronisation, but it never writes the
snapshot itself.

Two writers serialising overlapping state into one snapshot is a data-loss
hazard: each writer holds its own view of the other's half of the state, so a
write from either can silently overwrite the other's most recent changes with a
stale copy. Keeping one writer removes that class of loss entirely.

### 3. Notes merge on load; tasks are replaced

When the notepad loads, the local and server copies of each note are merged by
id: the copy with the newer `updatedAt` wins, and a local note the server has
never seen is kept. Tasks do the opposite — the server copy replaces the local
one.

The difference is deliberate and follows from what the content is. A task is a
brief form submission; a server-first replace is safe because a task the user
did not submit was never entered. A note is long-form text, and the cost of
losing one is high, so the notepad refuses to discard a local note merely
because the server has not heard of it yet.

To be plain about what this is: it is **protection, not a retry queue**. The
merge keeps a local note from being destroyed by an empty or stale server
response. Nothing is pushed to the server during init — no pending write is
flushed, and no unsent note is transmitted as part of loading.

### 4. Server sync for notes is debounced 1000 ms per note

A note's body is written to the server 1000 ms after the last change to that
note, rather than on every mutation. Debouncing is per note, not global, so
editing one note never delays or cancels another note's pending write.

A document body cannot be sent per keystroke: the volume of requests would be
enormous, and the server would spend its time persisting half-typed words. A
quiet period is the natural unit of "the user has paused", and one second is
long enough to coalesce a burst of typing and short enough to feel immediate.

### 5. The IndexedDB database moves to version 2, behind a guarded upgrade

The note store changes the object-store set, so `DB_VERSION` moves from 1 to 2.
The `upgrade` callback creates the three original stores only when the opening
version is below 1, and the `notes` store only when it is below 2.

The guard matters because a version bump re-enters `upgrade` for databases that
already exist. Re-creating a store that is already there throws
`ConstraintError`, which would fail initialisation for every existing user — the
one outcome the notepad's first release must not produce. Checking `oldVersion`
before each group of creations makes the upgrade add the new store and leave the
existing ones alone.

`STORAGE_VERSION` does not change: the localStorage payload simply gains two
fields, and the adapter fills in defaults for a payload written before notes
existed. The facade contract — `loadState`, `saveState`, `clear` — is unchanged
and evolves additively, as §7 of ADR-003 requires. Existing callers never break.

## Consequences

**Positive:**

- Notes persist locally at the same layer and through the same facade as tasks;
  no second persistence path is introduced.
- The single-writer snapshot means a note and a task written in the same session
  cannot clobber one another.
- Merge-on-load protects long-form note text from being lost to a stale server
  response.
- Debounced sync keeps a document body off the per-keystroke path.
- The guarded upgrade migrates existing databases in place, adding the notes
  store without disturbing tasks — verified by a test that opens a real v1
  database and upgrades it.
- The facade contract is untouched, so no existing caller changes.

**Negative:**

- The IndexedDB schema version advances, so the upgrade path is now a permanent
  part of the codebase and every future store addition must respect the same
  `oldVersion` guard.
- Client-generated ids are trusted by the server; uniqueness is the client's
  responsibility.
- Notes and tasks now share one snapshot, so the snapshot grows with note
  bodies rather than staying bounded by task count.
- The 1000 ms debounce means the very last edit before a close can be in flight;
  the local note is still safe, but a server round-trip may not have completed.

## Contract Stability

| Aspect | Guarantee |
|--------|-----------|
| Public methods | `loadState`, `saveState`, `clear` — stable |
| Evolution | Additive only; `PersistedState` gains `notes` and `activeNoteId`, `view` accepts `'notes'` |
| Backend | Unchanged — the notes store is an adapter detail |
| Schema | `DB_VERSION` 1 → 2, applied by a guarded upgrade; `STORAGE_VERSION` unchanged (1) |
| Migration | The task migration is undisturbed by notes; notes are never pushed during init |

## Relationship to the Roadmap

- **ADR-003:** the storage facade, its adapters, and the additive contract this
  ADR extends without breaking.
- **Session 005 (this ADR):** the notepad's model, persistence, and store.
- **Later sessions:** the local-first inversion and the repository above the
  facade are unaffected — the notepad is another consumer of the same seam.

Notes are a second payload on an existing boundary, not a new boundary. The
decisions here are confined to what the notepad adds: a store, a merge rule, a
debounce, and one guarded schema bump.
